# 地点・取り込み履歴の管理と地図（2026-09-10）

## 状態と判断

ユーザーの要望は、地点・録音群の編集／削除と、地図による地点登録・表示の検討。
本提案に対する「慎重に、できるだけシンプルになるようponytailで進めて」の了承を受けて実装。
以下を今回の範囲とする。操作確認の証拠は末尾とUXチェックリストに記録する。

編集・削除は必要。地図も座標の入力と誤りの発見に役立つため、地点の登録・管理に限って採用する。
結果・検索・検証・クイズの画面には地図や管理操作を増やさない。

## 利用者に見せる構造

既定の単位は引き続き「地点」。録音群を独立した分析対象に戻さず、管理画面で
「取り込んだ録音」として取り込み単位を表示する。

- 地点一覧：既存の「結果を見る」「録音を追加」に加え、控えめな「地点と録音の管理」の入口を一つ。
- 地点と録音の管理：地点名・場所を編集し、その地点へ取り込んだ録音を確認する。
- 取り込んだ録音：フォルダ名を初期名にし、録音期間・ファイル数・長さを併記する。
  必要なら名前を変更でき、取り込み単位でアプリから削除できる。
- 地点全体の削除：管理画面の下部。一つの確認画面で対象と影響を示す。
- 戻り先：常に地点一覧または地点の結果。編集途中の内容が消える移動では確認する。

新しい管理モード、録音群ごとの結果ページ、必須の録音群名入力は設けない。

## 編集・削除の意味

| 操作 | 振る舞い |
|---|---|
| 地点名／取り込み名を直す | 表示名を更新。再解析しない。過去に保存したレポートは当時の情報を保つ |
| 地点の位置を直す | 地図と座標を更新。変更前の位置で解析した結果であることを表示し、再解析へ進める。旧評価を新しい位置の品質保証に流用しない |
| 取り込んだ録音を削除する | 対象の登録・解析結果と、それに依存する検索／検証を削除対象として事前に数える。残す録音の解析結果を巻き込まない |
| 地点全体を削除する | その地点の登録と関連する解析・検索・検証・アプリ内レポート履歴を削除する |

元のWAV/FLAC、利用者が書き出したZIP等、独立して保存したクイズの音源・成績は削除対象にしない。
単に一覧から隠す処理を「削除」と呼ばない。削除確認には地点名／取り込み名、録音数、
関連する結果の件数を表示する。通常の名前変更に毎回確認ダイアログを出さない。

録音済みデータの時刻は、一般の地点編集で勝手に再解釈しない。まず編集を名前と座標に絞り、
録音の時刻の基準は表示する。タイムゾーンを誤って取り込んだ場合の訂正は、対象日時を
プレビューできる専用の訂正手順として別に詰める必要がある。

## 地図の最小構成

- 新しい地点の登録と地点の管理で同じ地図部品を使用。地図上をクリックしてピンを置く。
- 地点管理では保存した位置を表示。「場所を変更」するまでは誤ってピンを動かさない。
- 緯度・経度の直接入力も維持し、地図上のピンと同期する。地図を操作できない人やネットがない場面でも登録できる。
- 背景地図は一種類。拡大・縮小・移動・位置選択だけにする。
- 最初は航空写真、レイヤー切替、境界線描画、距離計測、地点比較、住所検索を追加しない。
- 地点一覧への常時地図表示は見送る。日々の主操作である結果の確認より地図を目立たせない。

実装はLeafletの基本機能とOpenStreetMapの背景タイル。座標選択のために
地図操作を自作するより保守範囲が小さい。地図部品は必要な画面でだけ読み込み、
解析やクイズの起動時間に影響させない。
[Leaflet公式の基本例](https://leafletjs.com/examples/quick-start/)

外部タイルはオンライン時の背景表示として扱う。アプリを識別するUser-Agent、出典表示、
通常のキャッシュを備え、一括先読みやオフライン地図のダウンロードは行わない。
地図取得失敗時も画面を待たせず、座標入力と保存を可能にする。
[OpenStreetMapタイル配信方針](https://operations.osmfoundation.org/policies/tiles/)

## データを守る実装

現在のコードでは、同じ地点の結果をいずれかのDataset IDから開き、`site_recordings`で
同じ地点の全録音を束ねている。解析ジョブ・検索・検証・レポートもDatasetを参照している。
したがってDataset行を単独で削除すると、残すデータや結果への入口まで壊れる可能性がある。

- 管理画面はSite IDで開く。結果への戻り先は残る取り込みから解決し、最初の取り込みの削除も検査する。
- 削除対象を依存関係から算出してプレビュー。地点を横断して削除しない。変更はDBトランザクションで確定する。
- 削除後にIDを再利用して、古いキャッシュやURLが別の音源を指さないようにする。
- 削除する取り込みを起点に、別の取り込みの録音まで解析したジョブが存在する場合を扱う。
  残す録音の解析・履歴は有効な地点内の参照先に付け替える。不要になった生成ファイルのみ除去する。
- 関連する検索・検証の一部の音を黙って消して、元の標本数や品質をそのまま示さない。
  該当する履歴全体を削除する場合は、その件数を事前表示する。無関係の履歴は残す。
- 解析・検索・出力等が対象データを使用中なら、終了してから編集／削除する。並行実行中の削除を許さない。
- 現在の解析開始は「両モデルの結果があれば完了済み」として除外する。
  座標変更後の再解析を実装する際は、解析時の位置も比較して、変更した地点を誤ってスキップしない。
- サーバーと画面側双方の一覧・録音・結果キャッシュを更新する。保存済みレポートのスナップショットを上書きしない。
- 別地点の検索が対象録音を参照している場合は削除を止める。他地点の検索を黙って消したり、過去の参照情報を書き換えたりしない。
- 関連レポートが削除される書き出し履歴もアプリから削除する。既に作成したZIPは残す。無関係の履歴は保持する。
- SQLiteのAUTOINCREMENTへ一度だけ移行し、外部キー・索引・トリガーを保持する。移行はトランザクション内で検査し、失敗した場合は元に戻す。

## 受け入れ確認

1. 新規地点で地図のクリックと座標入力が同期し、登録・再起動後も同じ位置を表示する。
2. オフライン／タイルエラーでも名前・座標の保存、録音の追加、結果の確認ができる。
3. 名前だけの変更で再解析は不要。位置の変更は旧解析と区別でき、再解析が実際に開始される。
4. 2地点、各2取り込みで、最初の取り込みと最後の取り込みをそれぞれ削除し、残る地点・録音・結果に戻れる。
5. 削除をキャンセルしたときは無変更。削除後も元音源と書き出し済み成果物のハッシュが変わらない。
6. 依存する検証・検索の件数と実際の削除範囲が一致する。別地点や独立したクイズの成績は保つ。
7. 作業中の削除、古いURL、削除直後の再取り込み、再起動を確認。古いキャッシュを表示しない。
8. 日英、キーボード操作、Mac実機で確認。Windows確認は既存のMac先行の合意を守る。
