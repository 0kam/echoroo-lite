# UI/UXレビュー（2026-09-24、Claude）

## 目的と方法

- 目的：鳴き声に詳しくない担当者（企業の環境部署・自治体職員）が、諦めずに使い、
  行政報告書に載せられる程度の妥当性を保った検出結果に到達できるかを評価する。
- 観点：(A) ソフトの存在意義（妥当な結果への到達）、(B) 認知的負荷（文言・情報量）。
- 方法：`docs/ux-direction-2026-09.md`・`docs/ux-checklist-2026-09.md`・`docs/requirements.md`
  を基準に、全画面のソースと日英の文言資源を読み、ブラウザ（1280×800）で実画面を操作した。
- 環境：Svelte開発画面 + sidecar。データは `.local-data/precision-audit-20260924` の
  DBと `release-qa-20260922` の解析ファイルを作業用にコピーして使用（実利用データは変更していない）。
  出力レポートは `exports/echoroo-1-f79329dfd8/index.html` を確認。
- 限界：開発者による専門家レビューであり、初見利用者の観察テストではない。
  Windows・Mac `.app`・実際の聞き取り作業の時間は未確認。

## 総評

機能は要件を満たしているが、**利用者が「自分は今どこにいて、次に何をすれば報告できる状態になるか」を
画面から読み取れない**。個々の文言は平易化が進んでいる一方で、注意書きと専門的な数値が同じ重さで並び、
最も重要な判断材料（この種の検出は信用してよいか、報告に載せてよいか）が埋もれている。
以下、影響の大きい順に記す。

## A. 存在意義に関わる問題（非専門家が妥当な結果に到達できるか）

### A1. 地点の結果ページに「次の作業」がなく、主ボタンが「レポートを書き出す」

- 画面：`#/datasets/1`。右上の唯一の primary ボタンが「レポートを書き出す」。
- 影響：解析完了直後、未検証の60種がそのままレポート化される導線が最も目立つ。
  「録音を聴いて確かめる」「探したい種が見つからない」は同列の補助ボタンに見え、
  検証が報告の前提であることが伝わらない。
- 案：ページ上部に地点の状態と次の一手を1行で示す
  （例「解析完了。報告の前に、主な種の検出が正しいか確かめましょう」→ primary「確かめる」）。
  「レポートを書き出す」は検証済み種がある、または利用者が未評価を承知で進む位置に置く。

### A2. 60種が同列に並び、1〜2区間の誤検出候補まで報告候補になる

- 画面：種一覧にコブハクチョウ・ダイシャクシギ・マガン（山地の1日録音で1〜2区間）が
  ルリビタキ（1,000区間超）と同じ扱いで並ぶ。レポート画面の「収録する種」は既定で59種すべてON。
- 影響：非専門家は「AIが出したのだから」と全種を報告書に載せる。行政報告として最も危険な誤り。
- 案（要件内）：一覧を3区分にまとめる。
  1. 確かさを評価済み（目標達成／未達を明示）
  2. 検出が多く未評価（「確かめる」を促す）
  3. 検出が少ない（既定で折りたたみ。「AIの誤りの可能性が高い。報告に使う場合は音を聞いて確かめてください」）
  レポートの既定選択は 1 と 2 のみ、3 は明示的に選ばせる（未評価種を「未評価」と明記して収録できる要件は維持）。

### A3. 「結果の確かさ」が良い／悪いを伝えない

- 画面：一覧の列は「未評価／確認中／評価結果あり」。種ページは
  「評価結果あり」「BirdNET · 正しい検出が90%以上とは、まだ確認できません」。
  実際の値（24.4%、つまり4件中3件が誤り）は「結果の詳しい数字を見る」の中。
- 影響：「まだ確認できません」は「作業が途中」と読める。評価は完了しており結果は「目標未達」。
  利用者は精度24%の種を報告に載せてしまう。
- 案：状態を結果で表現する。
  「正しい検出 24%（目標80%に未達）」「確認中 12/30」「未評価」「目標達成 92%」。
  主数値は隠さず、詳細（区間・閾値・母数）だけを折りたたむ。

### A4. 検証の入口が迂回路になっている

- 操作：フクロウの種ページ →「結果の確かさを調べる」→ 遷移先は「聞こえた生き物」一覧ページ
  （`annotations?view=list`）。そこに60種のチェックボックスがあり、フクロウが選択済み。
  ページ下端の「選んだ生き物を調べる」を押してようやくフクロウの検証が始まる。
  共通の10音がまだ保存されていない地点では、まず「録音の確認を続ける」で10音の聞き取りが必要だが、
  種ページではその前提が説明されない。
- 影響：押したボタンと表示されたページの見出しが一致せず、利用者は迷う。
- 案：種ページから直接、検証の開始画面（現在の「確認を始める」画面）に遷移し、
  そこで「まずこの地点の10音を聞きます（すでに保存済みなら省略）」と前提を示す。
  複数種をまとめて評価する導線は「聞こえた生き物」ページ側に残す。

### A5. 検証画面に2種類の回答手段が同居している

- 画面：`validation/7`（2種）、`validation/3`（1種）。
  上に「名前を選んでから、図の上で鳴き声の範囲をなぞってください」と範囲エディタ、
  下に固定バーで「聞こえる／聞こえない／判断できない」。
- 影響：必須なのは3択のみだが、画面はなぞる操作を主に見せる。
  2種の画面では見出しが「この生き物の声は聞こえますか？」（単数）のまま。
- 案：3択を主操作として上に置き、範囲指定は「聞こえる」を選んだときの任意操作
  （「どこで鳴いていますか？（任意）」）に降格する。設計文書でも「発声の境界描画を必須にしない」。

### A6. 作業量の見通しがない

- 画面：検証開始時「まず確認する音: 10」。開始後「30音中1音に回答済み」。
  その後モデルごとに最大30音、任意で見逃し評価30音が続くことは、途中まで知らされない。
- 影響：担当者が「終わりが見えない」と感じて中断する。存在意義に直結する。
- 案：開始画面に全体像を1行で示す
  「①共通の音10 → ②この種の音 最大30（2つのAI分で最大60） → ③任意：見逃しの確認」。
  進捗表示も「② 12 / 30」の形式に統一する。

### A7. 目標値が 90% と 80% で混在

- 画面：ルリビタキ（旧方式）は「90%以上」、メボソムシクイ（新方式）は「80%以上」。
  レポートには「基準調整時の90%は参考目標」「目標 80.0%」の両方。
- 影響：どちらが合格ラインか分からない。
- 案：文言は検証セッションの `target_precision` から生成し、固定の「90%」文言を廃止。
  調整用の目標を画面に出さない（出力のみに保存）。

### A8. 「報告できる状態」の定義が画面に存在しない

- レポートは「掲載した種と集計結果」「80.0%以上とは言い切れません」を淡々と並べる。
  読み手（上司・発注者）が「結局この種はいたのか」を判断する材料の整理がない。
- 案（要件に関わる提案）：レポート冒頭に3段の要約を置く。
  「確かさを確認できた種／確認したが目標未達の種／未確認の種」。
  アプリ側の種一覧区分（A2）と同じ区分を使う。

### A9. 参照音検索の結果が「確認を続ける · 2026-09-22 04:56:39」×5

- 画面：ルリビタキ種ページ下部。同じラベルのボタンが5つ、区別は作成時刻のみ。
- 案：「検索 #9 · お手本3音 · 回答 3/30」のように内容で区別し、最新以外は折りたたむ。

### A10. 独自モデルの参考値が誤解を招く

- 画面：「見つけた声のうち、正しかった割合: 100.0% (3 / 3)」「実際に…37.5% (3 / 8)」。
- 影響：3件の交差検証値が「100%」と大きく見え、下の「別の録音での確認」より目立つ。
- 案：作成時の参考値は既定で折りたたみ、「別の録音での確認」の結果を主表示にする。

## B. 認知的負荷（文言・情報量）

### B1. 注意書きが常設され、どの画面にも3〜5文の免責が並ぶ

例（地点の結果）：
「AIによる検出には誤りが含まれます。種を選ぶと、音・出現の様子・検証状況を確認できます。」
「検出数は15秒ごとに数え、2つのAIのうち多い方で並べています。」
例（種ページ）：「モデルの検出区間率。検証は利用者の判定に基づき、個体数を示しません。」
「この件数だけで録音全体の頻度や季節性は推定できません。」
例（検索の判定）：「未判定・不明は対象外に数えません。この判定だけで精度や不在が保証されるわけではありません。」

- 案：各画面の本文には「今すること」1文だけを残す。免責・単位の説明は「数え方について」等の
  1つの折りたたみに集約し、出力（レポート）では現状どおり全文を保持する。

### B2. 用語のゆれ

同じものが複数の語で呼ばれている（文言資源の出現回数）。

| 概念 | 使われている語 |
|---|---|
| 15秒／5秒の音 | 区間（60）、音（多数）、音源（37）、標本（3） |
| 判定の境界値 | 閾値（10）、基準（12）、表示閾値、境界 |
| 人が聞いて答える作業 | 検証（10）、評価（35）、確認（70）、確かめる、調べる |
| 検索に使う音 | 参照音（19）、お手本（4）、参照区間、参照音セット |
| 取り込み単位 | 録音群（16）、取り込み |

- 案：利用者向け画面は「音」「基準」「確かめる」「お手本」に統一し、
  「区間」「閾値」「標本」「録音群」はレポート・CSV・詳細折りたたみに限定する。

### B3. 内部値・英語・機械形式がそのまま表示される

- 図の脚注：「検証（95%区間） #2 · precision 24.4% [12.9–39.6%] · recall 100.0% [38.3–100.0%]」
  （`SpiralPlot.svelte:115` の固定英語）。
- 図の見出し：「BirdNET · 55f3e4055b1a」「閾値: 0.010 · 15 秒」。
- 鳴き声一覧：「2024-08-08T07:01:39+09:00 · 99.00–102.00 s」（30行）。
- 案：脚注は「確かめた結果：正しい検出 24%（12.9〜39.6%）」、ハッシュ・閾値は詳細へ、
  日時は他画面と同じ `Intl.DateTimeFormat` 形式（2024/08/08 7:01）にし、一覧は最初の5件＋「すべて表示」。

### B4. 見出し・ボタンが抽象的、または名詞のみ

- 見出し：「複数種の結果の確かさを調べる」「聞こえた生き物を選ぶ」「調べている種」。
- ボタン：「検証の結果」（遷移先は検証画面）、「確認を続ける」（検索の判定）、「結果を見る」（一覧ページ）。
- 案：見出しは「地点名 · 種名 · 今の作業」（例「ルリビタキ · 音を聞いて確かめる 12/30」）、
  ボタンは動詞で終える。

### B5. 長い一覧の羅列

- 種一覧60行、「まとめて評価する種」の60チェックボックス、聞き取り画面の60種パレット、
  鳴き声30行、参照音検索5件。
- 案：A2の3区分、パレットは「この地点で検出が多い10種＋検索」、鳴き声は先頭5件。

### B6. 英語UI

- 主要画面は成立している。「1 days」（複数形）、日時は地点時刻を維持していることを確認。
- 上記A・Bの修正は日英同時に行う必要がある（文言資源は3ファイルに分散）。

## C. 改善案の整理

### C1. 既存要件内で実装できる改善（Opusへの依頼候補）

1. 地点の結果：状態と次の一手を上部に1行、primary を次の作業へ。種一覧を3区分（A1, A2）。
2. 「結果の確かさ」を結果で表現、主数値を表に出す（A3）。目標値を `target_precision` から生成（A7）。
3. 種ページ →「確かめる」で直接、検証開始画面へ。前提（共通10音）を開始画面で説明（A4）。
4. 検証画面：3択を主操作に、範囲指定は「聞こえる」後の任意操作に（A5）。全体の工程表示（A6）。
5. レポート画面の既定選択を区分1・2のみに。区分3は明示選択（A2）。
6. 文言：図脚注・日時・ハッシュ・閾値（B3）、見出し・ボタン（B4）、用語統一（B2）、免責の集約（B1）。
7. 検索履歴・鳴き声一覧・独自モデル参考値の折りたたみ（A9, A10, B5）。

### C2. 要件・設計に関わる提案（ユーザーの判断が必要）

- レポート冒頭に「確認できた／目標未達／未確認」の3段要約を置く（A8）。
- 「検出が少ない種」の境界（例：10区間未満、または検出日数1日）を既定で折りたたむ基準。
- 独自モデルの交差検証値を既定で非表示にすること。
- 検証の範囲指定を任意操作に降格すること（独自モデル・根拠音の材料としては維持）。
