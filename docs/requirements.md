### UI の設計原則と中心となる流れ（2026-09-09 合意）

具体的な画面・操作の相談案は [種を中心にした操作フロー案](workflow-ui-proposal.md) を参照。
同文書の削除・統合一覧と画面試作は、以下の合意事項を具体化した未合意の案。

- UI の簡潔さ・使いやすさを優先し、最終成果に必要な機能へ絞る。
  「念のため」の選択肢やほぼ使わないオプションは設けず、既存の不要なものも削除する。
  不要な選択肢を詳細設定へ移すだけで残さない。利用者の判断が必要ない部分は適切な既定動作にする。
- 録音群を開くと解析結果の全体像が見え、気になる種から音・季節性・検証へ進む。
  解析完了後に結果を見るためだけの「報告作成」を要求しない。
- 検索は種をさらに調べる操作として結果画面へ組み込む。検出一覧に見つからない種を
  指定して参照音から検索し、人が確認した根拠を結果へ紐づける。
  モデル対応種でも検出が機能しない場合を含むため、対応種リストで検索への入口を制限しない。
- 検索対象の種名はフリーワードで入力する（ユーザー指定）。和名・英名・学名から
  種マスタ全体を検索し、検出された種だけの選択リストにしない。
  完全一致を優先し、表示は選択言語の一般名＋学名。未登録種にはユーザー追加の方針を適用する。
- 未検証の種も未評価と明示してレポートに含め、出力時に収録する種を選べる（ユーザー合意）。
- AI の検出と検索で人が確認した音は、同じ種に紐づけながら根拠と集計を区別する。
  両経路の集計には調整した閾値を全対象区間へ適用し、人が聴いた音だけに限定しない。
  検索で確認できなかったことを不在とは表示しない。
- 用語と操作を簡単にしても、検証条件・未評価・不確かさ・出力の再現性は維持する。
  画面配置と具体的な削除対象は引き続き確認し、採用済みの評価条件は表示・出力で一貫させる。

最終製品の利用の流れ（検出と検索の根拠・出力は区別し、操作は種を中心につなぐ。詳細は試作で確認）:

1. 調査地点と録音群を登録し、日時・位置情報を確認する。
2. BirdNET・Perch の分類結果から頻度・季節性を表示する。検証データに基づく種・モデル別閾値を
   全解析区間へ適用し、品質評価を添える。通常の検出一覧の個別確認・種名訂正は行わない。
3. 重要種等を検索する場合は、複数の参照音の区間を選び、種別に類似度を計算する。
4. 類似度範囲からサンプリングした音を対象種か判別し、その検証データで種・参照音別の類似度閾値を調整する。回答と根拠音を保存する。
5. 検出・検索とも閾値を全対象区間へ適用し、図・表・CSVを出す。検出区間率、検索の類似度・閾値以上の区間率、品質評価、個別の判定記録を区別する。
6. クイズで学習する。最初は koe-e-lab の26種を使い、素材追加は UI 上の範囲選択で行う。
   未見素材による能力評価と現地検証は [検証設計](validation-design.md) に従って区別する。

順序・優先度・必要性を相談する。最終構想と初回リリースの範囲は分ける。

### 展示までの機能範囲（ユーザー指定と詳細案）

- 音源フォルダ登録、日時・位置確認、BirdNET・Perch の分類、全録音の Perch 埋め込み、
  類似検索を最優先とする。「アップロード」は現行のローカル参照方針では取り込みを意味する。

  クイズと検証データ作成を含むフルワークフローを実装する（2026-09-09 ユーザー指定）。
  通常検出一覧の汎用的な訂正は初期版から省く。
- 音源 ID・区間・モデル版／設定・原予測・人の判断を区別して保存する。
  検証は実装範囲に含める。利用者にどの段階で検証を案内するかは UI の相談事項とする。
  検証なしで品質数値を作らず「品質未評価」と表示する案。
- spiral plot は展示で必須。full の検索・図のコードを読み取り確認済み。
  検出と検索の表示値・出力の詳細案を [reporting-design.md](reporting-design.md) に記録した。
- BirdNET・Perch 両方の分類結果の表示・比較を含める（ユーザー確定）。
  各モデルの原ラベル・スコア・区間・版を別々に保持し、片方で上書きしない。
  スコアの単純平均や、一致を正解・不一致を誤りとする自動判定は採用しない案。
- BirdNET の 3 秒窓と Perch の 5 秒窓はそのまま同じ検出行として扱わない。
  最初の比較表示は同じ録音／同じ再生範囲で両方の候補を並べる案。
  区間をまたぐ集計と評価の一致規則は別途定義する。
- 種マスタを BirdNET のみで構成する従来案は更新が必要。
  両モデルの版付きラベルと手動種を扱い、対応が確認できた種だけを統合表示する。
  同義語・分類差・未対応ラベルを誤って同じ種にまとめない。

### 地点・録音群の管理と具体例（階層は確定、操作詳細は提案）

従来どおり、一つの中央 DB 内で `Site > Dataset`。Project 層は不要とユーザーが確認した。
複数 Site と、その下の複数 Dataset を管理する。
習熟度・種マスタ・クリップライブラリは利用者全体で共有する設計を維持する。

Dataset は同一地点での録音群とし、年や録音機等の分け方は実際のフォルダ構成を基に相談する。

| Site の例 | Dataset の例 |
|---|---|
| 工場・北側緑地 | 2026 年定点録音、2027 年定点録音 |
| 工場・調整池 | 2026 年定点録音 |
| 中央公園 | 2026 年定点録音 |

1. 調査地点を作り、座標・タイムゾーンを登録する。
2. 地点に録音群を作り、音源フォルダを登録。日時の読み取りと欠測を確認する。
3. 後日回収したファイルは同じ録音群へ追加し、新規分を解析する。
4. 地点・録音群・期間で検索対象を指定し、両モデルの検出や類似音を確認する。
5. 地点を選んで比較し、対象期間・種・モデル・確認状態を選んで報告用の図を作る。
6. 次年度は新しい録音群を追加して年度間で比較する。

2026-09-10 実装確認：重複は実体を解決した絶対パスで判定する。別フォルダの同名音声は登録可能。
機器移動・交換時に録音群を分けるか、Dataset と camtrapDP の設置期間の対応は未決。地点別 DB や共有機能は先行実装しない。

### フォルダ取り込みの流れ（相談用の具体案）

1. 地点を選び、新規または既存の録音群を選ぶ。
2. PC にコピー済みの音源フォルダを指定する。サブフォルダを含めて走査し、
   `地点/音源.wav` と `地点/回収日/音源.wav` の両方を同じ操作で扱う。
3. ファイル数・合計録音時間・日時範囲・形式・読み取れないファイル・登録済み件数を
   プレビューする。今回の実物なら「24 本、12 時間、2024-08-08」と表示する。
4. ファイル名の日時の読み取り例と、地点に設定したタイムゾーンを確認して登録する。
   日時が読めない音源をファイル更新日時から黙って補完しない。
5. 後日回収したフォルダを既存の録音群へ追加し、未登録分を登録・解析する。

フォルダ構造から地点を自動確定せず、回収日のサブフォルダを別地点・別録音群に
強制変換しない。Dataset はアプリ内の論理的なまとまりであり、複数の回収フォルダを
追加できる案。原音源を参照し、元の名前・配置は変更しない。

### 地点の時刻とアプリのロケール

ユーザー確定の方針は「録音日時は基本的に設置場所のローカルタイム」と
「ロケールを切り替え可能にし、国内イベント向けの初回プレビューから日本語も提供する」。
以下を実装時の設計方針とする。

- **地点のタイムゾーン**は Site に IANA 名（例: `Asia/Tokyo`）で保持する。
  オフセットのないファイル名日時はその地点の時刻として解釈する。
  録音機が別の時刻設定だった場合は、取り込みプレビューで明示して補正できるようにする。
- 録音時刻は内部の比較・交換用 UTC と、元の読み取り日時・取り込み時に適用した
  タイムゾーン／オフセットを保持する。地点の設定変更だけで既存録音の時刻を再解釈しない。
  夏時間切替で二通りに解釈できる時刻や存在しない時刻は黙って補完しない。
- 録音一覧、日別・時間帯別集計、spiral plot は基本的に地点のローカルタイムを使う。
  複数タイムゾーンの地点を比較する図では、各地点の現地時刻での比較と分かるようにする。
  PC のタイムゾーンや UI 言語を変えても、録音が別の日付・時間帯へ移動しない。
- **アプリのロケール**は利用者全体の設定として地点と分離する（例: `en`, `ja`）。
  メニュー・説明・エラー・日時／数値の表示形式に適用する。初期値は対応する OS ロケール、
  未対応時は英語とする。**初回から日本語・英語を同梱**し、日本語環境では日本語を初期表示する。
  選択したロケールは保存し、再起動後も維持する。
- UI 文言は最初からメッセージキーと翻訳リソースに分け、画面コードへの直書きを避ける。
  日時・数値は標準の `Intl` 等を使い、地点のタイムゾーンを明示して整形する。
  部分翻訳は英語へフォールバックし、文字列の連結で文章を組み立てない。
  初回プレビューで提供する画面は、取り込み・解析・比較・検索・設定の文言に加え、
  進捗・空状態・確認ダイアログ・利用者向けエラーも日本語で操作を完結できるようにする。
  日本語表示時の文字切れと未翻訳文言をプレビューの受け入れ確認に含める。
- 種名は **選択言語の一般名＋学名**。2026-09-08 のユーザー希望を受け、初期版は
  **BirdNET の名前＋ユーザー追加／上書き**とする。同じ言語内ではユーザー名を優先し、
  未登録時は英語、次に学名へフォールバックする。日英を同梱し、オフラインで使える。
  学名・不変のローカル UUID・モデルの原ラベル・表示名を分ける。Perch も学名が完全一致
  する種には共通の名前を使い、異名・分割種を自動統合しない。full の COL／IOC／鳥学会／
  iNaturalist の多段解決は初期版に導入しない。詳細は [種名と外観](species-and-branding.md)。
- 外観は Echoroo full の配色とロゴを使用する（同日のユーザー指定）。暖色のライト配色と
  紫系のダーク配色、ローズ系アクセントを使い、オレンジの既存ロゴを流用する。
- 機械向けの出力は固定の列名と ISO 8601 の日時（UTC または明示オフセット）を使う。
  ロケールを変えても CSV 等の解析方法が変わらない。報告用グラフの表示文言はロケールに従う。

UI 着手時の確認例: `Asia/Tokyo` の 06:00 の録音を、英語 UI／別タイムゾーンの PC でも
地点の 06:00 として表示・集計できること。言語変更で変わるのは文言や表示形式とし、
録音の同一性・時刻・解析結果は変わらないこと。現 PoC は翻訳 UI を持たない。

### 公開・報告に必要な振る舞い（提案）

- 図と出力には検出／検索の経路、原予測・確認根拠・補正推定値の別、対象期間・地点・
  モデル版又は参照音群・閾値・集計単位を残す。種一覧・根拠音源・図・CSV はユーザー合意。
- グラフ上で録音なし、未解析、解析済み未検出を区別する。
  録音努力が異なる比較では、検出数だけでなく録音時間／有効録音数を考慮する。
- spiral plot は full の日付×時刻の配置を参照する。検出は共通窓の検出区間率、
  検索はセル最大類似度を初期表示し、閾値超過区間率を併記する案。
  個体数とは呼ばない。詳細な集計・書き出し案は [reporting-design.md](reporting-design.md) を参照。
- 類似検索で見つけた音は根拠区間として保存する。検索で見つからなかった場合は
  調査範囲での「未確認」とし、その地点に生息しないとの判定に置き換えない。
- BirdNET スコアを正答確率として表示しない。公式ツールも種ごとの検証を扱い、
  confidence は真の確率ではないと説明している。
  [birdnetTools 公式資料](https://birdnet-team.github.io/birdnetTools/articles/birdnetTools.html)
- クイズを種別の判定能力の評価にも使い、評価時点・問題セット・見逃し・誤認・保留を
  検証記録に添える案。学習用の総合正答率をそのまま現地ラベルの正しい確率へ変換せず、
  未見の正解確認済み問題と現地条件への適用性を区別する。
  本人確認・保留の記録を残し、判断がつかない音を無理に正解扱いしない。
- 2026-09-10 ユーザー追加要件：利用者のテスト成績を、検証データの信頼性の評価と
  レポートへ反映する。具体的な計算・表示・採用条件は [Astraレビュー](report-review-astra-2026-09.md) の提案を参照する。
  成績を検出数へ掛ける方式や、一律の合格点を採用することまで合意したものではない。

### 負担を抑えた評価（採用済み方針と残る拡張）

ユーザー案は、モデル検出の有無によらずランダムな音声セグメントに人が
アノテーションを付け、見逃しを含めた性能を測ること。さらに種別の閾値調整と
precision / recall に基づく重み付きの報告について検討を希望された。
採用したprecision評価と、任意のrecall・頻度補正の残る設計は
[検出品質の検証と報告値の補正](validation-design.md)を参照。閾値調整、precision評価、recall評価を分ける。

- 最初は対象種を一種〜少数に絞り、短い固定区間に「聞こえる／聞こえない／
  判断できない」を付ける案。周波数枠や全種の網羅同定を必須にしない。
- 評価用区間は対象範囲全体をカバーする確率抽出とし、抽出規則と対象範囲を保存。
  負担を減らす案としてスコア帯ごとの層化無作為抽出を検討する。低スコア・未検出区間も
  抽出し、層ごとの抽出率で全体へ重み付けする。単純無作為抽出は比較基準とする。
  前後の音も再生できるが、採点対象の区間は明示する。
- UI は少数ずつ判定して中断・再開できる形にする。必要標本数の保証はしない。
  正例数、未判定数、不確かさを示し、正例がない種の recall は算出不能とする。
  希少種では無作為抽出だけで十分な正例が得られない可能性がある。
- 確認を効率化する検出候補・類似検索の優先提示は別の作業として用意できるが、
  その結果をそのまま無作為評価の母集団へ混ぜて recall を算出しない。
- 2026-09-10 ユーザー追加要件：クイズは出題時からスペクトログラムを表示する。正解の種名や元のファイル名は回答前に見せない。
- クイズと評価で再生・スペクトログラム・回答操作は共有できる。
  評価では AI の答えを先に見せない案とし、クイズ素材や学習済み音源での成績と区別する。
- クイズで検証者の種別能力を測る追加案は [検証フロー第 6 節](validation-design.md#6-人の判定の品質と負担の限界)
  を参照。学習・能力評価・現地検証を区別し、確認済み問題の作成と評価結果の保存を
  最小構成として検討する。人の誤りの数値補正は現地への適用性を検証してからとする。
- クイズ素材は xeno-canto とオリジナル音源から登録でき、区間は UI の範囲選択で指定する
  （ユーザー合意）。操作案は、波形・スペクトログラム上で時間範囲を選び、両端を調整し、
  選択範囲の再生・ループ再生で確認して保存する流れ。時間範囲の選択を基本とする。
- 拡張案として、他種や環境音に対する相対音量・重なりを変えて練習問題を作る。
  [検証設計のクイズ拡張案](validation-design.md#クイズ素材の選択と合成による難易度変更拡張案)
  に、原素材と合成条件の保存、学習と能力評価の区別を記録した。
- 非専門家の判定に対する一致度として解釈し、人の判断そのものを無条件に真値としない。
  保留を除いた見かけの精度だけを報告しない。十分な評価をどう定義するかは引き続き相談する。

## 2. 従来設計から引き継ぐ前提

- 一人用、コア処理はオフライン、ログインなし。Windows を第一対象とする。
- Tauri + SvelteKit + Python sidecar、中央 SQLite、音源は参照で保持する。
- BirdNET による検出と地域フィルタ、Perch V2 による音響類似検索。
  今回 Perch の種分類表示・比較も追加が確定した。
- Site > Dataset、和名表示、手動種追加、camtrapDP 出力を想定する。
- モデル学習、共同編集、投票、サーバー基盤は対象外。
- コード・コメントは英語、日本語で相談する。初回 UI は日本語・英語の両方を提供し、
  ロケール切替と将来の翻訳追加が可能な構造にする（ユーザー指定）。
- 本リポジトリでは Ponytail full を常時適用する（今回のユーザー指定）。

これらも今回の相談で変更可能。few-shot 検出は従来文書内でも「モデル学習なし」
と衝突するため、自動的に M3 の要件へ含めない。

下記の項目を優先する。展示・報告設計と新規precision評価の条件は了承済み。source web QA、Mac配布物作成、変更したMacネイティブ操作を確認した。利用者の作業時間、実録音での識別性能、Windowsは未確認。

| 正解データ | AI 候補の確認だけでは見逃し数が得られない | 対象範囲・対象種を明示し、検出外も抽出対象に含めた標本の区間を判定する。全録音の全区間を人が確認する要求ではない。保留・未回答・陰性と、調整用・評価用を区別する |
| 検証の負担・訂正 | 長い評価を強制せず、誤操作を直し、途中保存できる必要がある | 新規precision評価は1種・1モデル最大30件を固定し、全件回答後だけ片側95%下限80%を判定する。途中回答は保存・訂正できるが保証・自動合格には使わない。旧セッションは保存済み方式を維持する。詳細は検証仕様 |
| 時間範囲の注釈と独自分類器（2026-09-14の相談） | 声の位置を保存し、レポートとPerch転移学習へ再利用したい | 2026-09-15に範囲の記録・訂正・出力と、一種で追加学習を試す方向性を了承。[相談案と実装状況](annotation-and-custom-model-proposal-2026-09.md)を参照。2026-09-16に範囲の記録・訂正・HTML／CSV／JSON出力を実装。2026-09-22に、現行機能を点検・修正した後で独自分類器の実装へ進むことを了承。固定したPerch埋め込みと既存の検証・検索判別を再利用し、作成・性能評価・推論・レポートをMacで確認する。確認区間・声の範囲・未解決を区別し、CV内の調整と最終モデルの独立評価を分ける。実装完了や実際の識別性能は、了承だけでは確認済みにしない |
| 複数種をまとめる検証フロー（2026-09-15の相談） | 同じ音を繰り返し聴く手間を減らし、AI未検出の声・種不明の声も残したい | 種の入力は、録音全体のAI検出種を初期セットにした共通リストから選ぶ。音ごとのAI予測を提示する意図ではない（ユーザー訂正済み）。[具体案と操作見本](annotation-and-custom-model-proposal-2026-09.md)の流れを了承し、2026-09-16に本番実装。15秒全体から縦横別にも拡大し、複数種の時間範囲を指定する。共通の層別標本→不足の種別有無確認→別録音での評価へ進む。抽出数や層配分は実装上の初期値で、最適性は今後実データで評価する。未記載を陰性にせず、リストの版・追加履歴・確率標本の条件を保持する |
| 出力と復元 | camtrapDP だけでは習熟度・設定・埋め込み・音源を復元できるとは限らない | 研究用の出力とアプリ状態のバックアップを分ける。CSV、Raven 等の必要性と受け取り先を確認する |
| 種の同一性 | 学名変更から UUID を再計算すると別の種 ID になる | 不変のローカル ID と版付きの外部対応を分ける案。UUIDv5 を採用する場合も生成名・正規化・改名・分割統合規則が必要 |
| UI 言語 | 国内イベントの利用者が日本語で操作を完結できる必要がある | 初回から日本語・英語を提供。翻訳リソースを使い、表示ロケールは地点のタイムゾーンとは分離する |
| クイズ | 正解率をそのまま野外同定能力と解釈できない | xeno-canto と希望種セットからの作成は最終要件。選択式／自由回答／不明、複数種音声、同一音源の再出題、習熟度表示の意味を決める |
| 初回導入 | 初回モデル取得にはネットが必要になる | 2026-09-30、BirdNET・Perchを.app／.exeに同梱し、DL直後からオフラインで使える方針を了承。モデル更新はアプリ更新と同時。BirdNETモデル（CC BY-NC-SA）の再配布・業務利用条件と帰属表示の確認は、公開配布の前提として未解決のまま残す |
| 検出・埋め込みモデルの構成 | 主な利用者（企業・自治体）の用途がBirdNET 2.4のNC条件に当たるか明確でない | 2026-09-30に了承：埋め込みはPerchに固定する（プレビュー版モデルでは作らない）。標準は商用利用できるPerchのみの構成とし、BirdNET 2.4＋Perchは利用条件を明示した選択肢として用意する。BirdNET+ V3.0（CC BY-SA、商用可）はプレビュー版のため当面採用しない。Perchの候補は両版とも日本鳥学会「日本鳥類目録 改訂第8版」掲載種で絞りPerchの学名へ名寄せする。和名はBirdNET由来をやめ目録とWikidata（CC0）から作る。eBirdの種コード・リンクは削除する（2026-09-30了承、設計は[model-editions-2026-09.md](model-editions-2026-09.md)）。選択肢は別配布（NCファイルを含まない標準版と、非営利向けのBirdNET付き版）とすることを了承。BirdNETは別エンジンとして扱うため地点単位の選択は不要 |

全録音を重なりなしの 5 秒窓で埋め込むと、1 時間あたり 720 ベクトル。
float32 × 1536 次元で約 4.42 MB/時、1,000 時間で約 4.42 GB
（ベクトル本体のみ、10進単位。DB の追加領域は別）。
この計算はサイズの概算であり、検索速度の検証ではない。
ユーザーのプロトコル（1 地点、平年 365 日、欠測なし）では以下になる。

| 項目 | 1 地点・1 年 |
|---|---:|
| 1 分録音の本数 | 17,520 |
| 音声の合計時間 | 292 時間 |
| Perch 5 秒窓、重なりなし | 210,240 ベクトル |
| 埋め込み本体（float32 × 1536） | 1,291,714,560 bytes ≈ 1.29 GB（1.20 GiB） |
| BirdNET 3 秒窓、重なりなし | 350,400 窓（検出結果の件数ではない） |

地点数・年数に比例して増える。窓の重なりを増やした場合は再計算する。
元音声・DB の追加領域・推論メモリ・キャッシュは別。
この Mac は M4 Pro・24 GiB メモリであることを `sysctl` で確認した。
今回の 12 時間のテスト音源では Perch 分類・埋め込み・DB 保存検索に 186.96 秒、
BirdNET 分類に 79.80 秒（モデル取得を除く PoC 処理時間）だった。
8,640 件の検索確認は 19.41 ms（旧PoC）。現在のアプリによる年間負荷試験では
210,240区間の試行検索78.33秒、2種・各2参照区間の保存検索168.27秒を測定した。
年間プロトコルは短いファイルが多く、ファイルごとの固定費も異なるため、
音声時間だけの比例計算を年間の実測結果として扱わない。

検証順序の提案: 実音源で 1 日分 → 1 か月分 → 1 年分。
読み込み・前処理・両モデル・保存を含む全工程、最大メモリ、検索時間を測る。
各段階の実測から翌段階の所要時間を見積もり、途中取消・完了分保持も確認する。
まず現在の CPU 経路を測り、性能目標に届かない部分だけを改善する。
最低合格条件は **1 地点年を 12 時間以内**（ユーザー確定）。地点数の上限は未合意。
M4 Proの凍結サービスでは年間相当の17,520本を検索・報告出力まで4時間8分25秒で完走した。
入力を反復する負荷試験の条件と年間GUIの確認は [測定記録](annual-benchmark-2026-09.md) を参照。
Windowsでの達成は未検証。PC全般での性能や検出品質を保証する値ではない。

## 4. 引き継ぎ文書の要修正点と検証課題

### 実測と未検証を区別する

- レビュー開始時は文書と PoC のみだった。現在は登録・解析・再生・日英種名表示が動く。
  最新の実装範囲は [implementation-status.md](implementation-status.md) を参照。
- Perch の parity は過去の Linux 環境で合成音声 6 窓について記録された結果。
  今回再実行した結果ではない。
- 約 12 秒/30 分は、`poc/onnx_parity_bench.py` の合成音声 1 窓を 30 回処理した
  速度から 360 窓へ換算した値。読み込み・再サンプリング・BirdNET・DB 保存・
  モデル起動を含む実音声全工程の時間ではない。
- 旧 PoC は `embedding` 出力だけを要求していた。今回の Mac PoC では Perch の
  分類出力 `label`（14,795 次元）と埋め込みの両方を取得して性能を測定した。
  ラベル表は版・ハッシュを記録し、分類スコアは生の logit として保存した。
  現アプリは全 Perch スコアと、地域フィルタ内の全 BirdNET スコアを保持する。
  モデル間は学名の完全一致で表示名を共用する。同日の追加修正で Perch も BirdNET の
  地域リストに限定した。その後のユーザー指摘を受け、通常画面は両モデルとも地域フィルタを
  常時適用し、Perch だけにあった切り替えは削除した。Perch の表示スコアは
  全クラス softmax による0〜1とし、その後に地域で絞る。元 logit は保持し、未較正と明示する。

  日本語切り替え・再起動後の保持とモデル取得も通過。BirdNETの起動停止を修正し、30秒実音声の両モデル解析・検索・報告書き出しも通過。
  実音声の検索品質も未評価で、M0全体は未完了。
  配布の最新結果は [Windows展示版の準備](windows-preview.md) を参照。

  これは LiteRT 全方式の不可能を意味しない。利用するパッケージ・モデル・版を

  上記の Mac 検証にはこの経路を使った。[配布一覧](https://pypi.org/project/ai-edge-litert/)

### 配布・保存・交換

- Windows CI はプロセス起動だけでなく、凍結した sidecar で BirdNET 検出・
  地域モデル・Perch 推論・sqlite-vec 保存検索を通す必要がある。
  配布版のインストール、音声再生、スペクトログラム、終了処理は別の確認項目。
- localhost API はログイン不要でも、loopback bind、アプリからのアクセス制限、
  任意のローカルファイル読み書きを許さない境界設計が必要。
- 稼働中 DB を NAS・同期フォルダへ置くことを無条件に保証しない。
  ローカル DB と停止中／整合したバックアップの転送を分ける案。
  SQLite はネットワーク越しのファイルロックや同期の信頼性に注意を求めている。
  [SQLite 公式資料](https://www.sqlite.org/useovernet.html)
- camtrapDP はカメラトラップ向けの定義を持つ。音声の時刻・区間、Site/Dataset の
  意味、受け取り先との互換性を検証し、標準準拠と独自拡張を区別する。
  [Camtrap DP データ定義](https://camtrap-dp.tdwg.org/data/)
- 種 ID の一致だけでは Lite 間交換は完成しない。音源・解析・手修正の対応、
  競合、取り込み仕様も必要。交換機能自体の初回要否を先に確認する。
- モデル・同梱和名・任意取得クリップの配布条件、出典、版とハッシュを記録する。
  目録8版の同梱可否の法的結論は今回再検証していない。現行の利用者持ち込み方針を維持する。
- full の検索・spiral plot のコードは版を固定して読み取り確認した（[記録](reporting-design.md)）。
  同梱データ全体の監査・実 UI の動作確認は未実施。流用時には対象ごとに確認する。

## 5. 開発と受け入れ確認の順序

1. 確定した Site > Dataset と両モデル分類を基に、取り込み・解析・保存・結果表示を実装する（着手済み）。
2. 一つの地点と録音群を例に、取り込み → 検出図、又は参照音選択 → 検索・判別 → 出力の画面・操作を確認する。
3. 上記のうち DB・解析方式に影響する仕様を確定する。
4. M4 Pro で実音源の解析を測り、Windows の配布実行も M0 内で早期に検証する。
5. ユーザー指定の `whombat_data/test` と対象規模のデータで以下の受け入れ条件を検証して M1 に進む。

| 受け入れ項目 | 判定方法 | 未決の数値・条件 |
|---|---|---|
| オフライン | 導入を終えた配布版でネットを切り、取り込み・解析・検索・保存を完了 | 対象 Windows 版・CPU/RAM |
| 検索の有用性 | 既知の例音から、BirdNET が見逃した別区間を検索して人が正例を判定 | 評価クエリ数、上位 K、必要な成功割合 |
| 性能 | 実録音の全工程時間、最大メモリ、DB サイズ、検索待ち時間を測る | 録音時間数と許容時間 |
| 判定の保存 | 検証／検索の対象種判定・根拠を再起動・再解析後も参照できるか確認 | 解析・参照音群の版変更時の対応規則 |
| 復旧 | 処理取消、失敗、音源移動後に再実行・再リンクする | 再開粒度、音源同一性の確認方法 |
| 評価 | 小さな既知の正解例で TP/FP/FN と閾値別値を手計算と照合 | 評価単位と時間一致規則 |
| 出力・復元 | 受け取り先で出力を読めること、別途バックアップから状態を復元できること | 必要形式、バックアップ対象 |

## 2026-09-13：HTMLレポートと保存時点の根拠

- 保存先の選択一回で、本文・表・図・音声を読めるHTMLフォルダと共有用ZIPを作る。PDF／DOCXの形式選択は置かない。本文・表のコピー、図のPNG保存、CSVと再集計用スコアを提供する。
- 地点と画面の対象期間を使用し、期間に重なる録音ID集合を固定する。同じ地点の取り込みはまとめる。比較・重点種選定は追加しない。
- 検出15秒・検索5秒の完全区間で、閾値の以上／未満、図・集計・スコアCSVを一致させる。検索で基準が決まらないときに0件や探索用中央値を採用値として示さない。
- 検証・検索の回答時点の練習成績を保存する。現在のクイズは練習であり、未見音による能力評価が存在するとは表示しない。成績による検出数や品質の数値補正をしない。
- 保存後の音声・成績・解析の変化で、過去の一式を上書きしない。元の参照音がなくなった場合は理由を示す。
- Mac同梱版の実音声解析・検索・HTML一式生成を確認。Windowsへは進めていない。ブラウザのローカルファイル閲覧制限により、オフラインでの直接閲覧とWord上の貼り付け体裁は受け入れ確認が残る。
